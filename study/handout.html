01 System architecture

Next.js 16 (App Router) and React 19, deployed on Vercel. Data lives in Supabase Postgres, but every table stores one JSONB blob per row rather than real columns. The schema lives in the application code, not the database.

The db.js contract

Every API route talks to the database through exactly three functions, regardless of backend: readDB(), writeDB(db, touchedCollections?), nextId(db, prefix). lib/db.js picks between two implementations based on DB_BACKEND: a local JSON file (data/db.json, used for local dev) or lib/db-supabase.js (real Postgres, used in production). Both expose the identical signature, so no route needs to know which one is active.

Gotcha: read_full_db() is hardcoded

readDB() calls one Postgres function, read_full_db(), which explicitly lists every collection by name in a jsonb_build_object(...) call. It is not a dynamic loop over existing tables. Adding a new collection to the JS-side COLLECTIONS map makes writes work immediately, but every read silently returns an empty array for it until read_full_db() is manually edited to add the new field. No error. Just silent data loss from the app's point of view. Always fetch the current function body first (select pg_get_functiondef('public.read_full_db()'::regprocedure)) before changing it.

Writes are targeted, not snapshot-replace

As of August 2026, writeDB() upserts only the rows it's given. It never deletes anything implicitly. Real deletions go through a separate, explicit deleteRecords() call naming the exact ids being removed. This replaced an earlier design where every write replaced a whole collection with the calling request's in-memory snapshot, which had two real consequences documented in Incidents & fixes below. Read that section before changing anything in lib/db-supabase.js.

Id minting

Record ids (INV-0001, TKT-0042, etc.) are minted by a Postgres function, increment_counter(prefix), which does the read-and-increment as one atomic UPDATE. This makes nextId() async on the Supabase backend, so every call site awaits it. The JSON backend keeps its own in-memory self-heal logic (checks minted ids against real data on first use per prefix, per request) since a single local process has no concurrent-request race to guard against.

Auth model

Session-based, checked per-route via helpers in lib/authz.js. Four gates cover every route in the app:

02 Accounts & roles

Seven real account types, plus four self-service "pre-accounts" that exist only to be converted into a real one.

Management
Runs everything. The only role that passes every auth check.
Teacher
Delivers classes, self-reports attendance, gets paid via Paychecks.
Staff
Internal roles (ops, marketing, etc.), billed the same way as Teachers.
Student
Enrolled in Services, billed via Invoices.
Parent
Views/acts on behalf of linked children (StudentIDs).
Ambassador
Referral/outreach role, billed like Staff.

Self-service pre-accounts: TrialAccTeacherInterviewAccStaffInterviewAccAmbassadorInterviewAcc. Each converts into its matching real account type once Management approves the underlying trial/interview.

03 Billing logic

The rate hierarchy

A Service holds one or more Components, each holding one or more Batches, the level someone actually enrolls into. Each Batch offers one or more Rates. Duplicate currencies are allowed on the same Batch (two different USD tiers, say), so a rate is identified by its own id, never by its currency. An Enrollment locks in one specific BatchID + RateID. Every billing calculation resolves through that pair, never through the Service directly.

Billing typeFormulaNotes
Monthly (default)(rate / scheduledHours) × attendedHoursProrated by actual attendance against what was scheduled.
Hourlyrate × attendedHoursFlat per-hour, no proration against scheduled hours.
OneOffrate (flat)Not hours-based. Generated once per enrollment, ever, regardless of how many months pass.

Currency conversion

Every Invoice/Paycheck carries its own currency amount plus an INR figure (INRAmount) for internal accounting. Conversion rates come from a free public API (fawazahmed0/currency-api, ~340 currencies, no key required), fetched once per currency-and-month and cached in db.fxRates. Critically, the rate used is always the 1st of the invoice's own month, not the day it happens to be generated or edited. A July invoice created in September still prices at July's rate. If no rate can be found, INRAmount is left at 0 for Management to fill in by hand. It's never silently guessed.

Payment reconciliation

INRDue defaults to the full INRAmount when an Invoice or Paycheck is created. A Student marking an invoice paid (or Staff marking a paycheck received) is a self-report: it sets a flag and a timestamp, and requires a payment-proof attachment on the Invoice side. It does not by itself change INRDue.

Management approves the claim explicitly: when a row shows the paid/received flag but INRDue is still above zero, the row surfaces an Approve control. One click zeroes the due (full payment), or Management enters a custom remaining amount (partial payment). This closes the loop between "someone claims they paid" and "the books actually reflect it."

Duplicate detection

The Billing tab flags any student/month or staff/month with more than one Invoice or Paycheck. This is informational, not a hard block, since a second record in the same month can be legitimate (a separate OneOff purchase alongside a Monthly subscription, for instance).

04 Scheduling logic

Occurrences → ScheduleItems

A Batch's recurring weekly slots are defined as Occurrences (day, time, duration, timezone). A background process, ensureScheduleGenerated, expands these into concrete dated ScheduleItems roughly one month ahead on every relevant request. Nothing needs to be manually "generated" for a normal week to appear on the calendar.

Two separate reschedule paths

A self-service reschedule request (Student/Parent/enrolled account) is Pending until Management approves or rejects it. Approval sets the same RescheduledDate/RescheduledTime fields a direct edit would. Management's own direct reschedule (editing a ScheduleItem from the admin Schedule tab) applies immediately, no approval step, since Management is the approver for the other path too.

Trial vs Interview booking

Trial accounts pick a specific open slot directly from a self-service pool, scoped to Student-open Services only. Interview accounts (Teacher/Staff/Ambassador tracks) don't pick a time at all. They request against a Service, and Management assigns the actual slot only once approving the request. This was a deliberate design change: candidates never see or choose a specific interviewer's slot in advance.

05 Account lifecycle

Public applications → pre-account → real account, in three stages.

  1. RegForm submission: a public applicant fills a form naming what they're applying for (Trial, TeacherInterview, StaffInterview, AmbassadorInterview).
  2. Approval: Management approves or rejects. Approval mints a new pre-account (e.g. TIN-0004, a TeacherInterviewAcc) with an auto-generated username and password, shown once to Management to hand off.
  3. Conversion: once the trial/interview process concludes favorably (Trial: Management adds the trialed Service directly; Interview: candidate submits a task, Management sends an offer, candidate accepts), Management runs Convert, which replaces the pre-account with a real Teacher/Staff/Ambassador/Student account, carrying history forward.

06 Incidents & fixes

Two real production incidents, both from the same root cause: deriving a write from a stale in-memory snapshot instead of a database-atomic operation. Worth knowing before touching lib/db-supabase.js again.

18 Jul 2026: 17 of 18 users deleted

A direct Supabase RPC call updated one user's timezone by passing only that single row to sync_table. sync_table upserted the given row and deleted every row not in the given id list. Passing one row wiped out the other 17. Recovery required manually reconstructing profiles from chat history; several fields were unrecoverable guesses. This is the origin of the standing rule: never call the database directly, always go through the app's own API/CLI/MCP, always back up first.

21 Aug 2026: concurrent writes silently deleted each other's records

The same sync_table mechanism, triggered organically this time: two concurrent requests writing the same collection each read the table before the other's insert landed, so each one's snapshot excluded the other's new row. Whichever write ran last deleted the other's record. Reproduced live: 8 concurrent ticket creations left only 1 of 8 behind. Fixed by splitting the function into upsert_rows() (insert/update only, never deletes) and a separate, explicitly-targeted delete_rows(). Real deletions now name their exact ids instead of being inferred from what's missing off a snapshot.

Same day: id minting raced under concurrency too

nextId() incremented a counter purely in memory, so two concurrent requests could read the same value before either wrote it back, both minting the identical id. This had already hit production twice (paychecks, attendance) as an "ON CONFLICT" error. Fixed by minting through a single atomic Postgres UPDATE instead, so concurrent callers are serialized by the database rather than racing on JS-level state two separate serverless invocations can never actually share.

07 Working preferences

Standing agreements for how work gets done on this codebase, reinforced over the course of this engagement.

Never write to the database directly
Always through the app's own API routes, the dcp1 CLI, or the MCP server. Back up before any destructive command. Why: the 18 Jul incident above.
Confirm before fixing; one ticket at a time
Present findings and a plan, wait for explicit go-ahead, even after root-causing an issue. For vague tickets missing location detail, ask directly rather than guessing or shelving.
Never test against real records
Create disposable, clearly-labeled test data before any live click-through verification, then clean it up fully. Why: a verification pass once rejected a real applicant's regform by targeting "the first row" instead of a disposable one.
Save verification screenshots to snapshots/
Never scratch-and-delete. The user should be able to independently confirm what was checked.
Commit after every file change
Conventional Commits format; git log is the state record. No separate session-summary files.
No em dashes, no AI writing tics
Plain, active-voice sentences (Orwell's six rules + ASD-STE100's structural rules) in chat, code comments, commits, and changelog entries alike.

08 Release process

Commits follow Conventional Commits (feat / fix / docs / chore / refactor / perf), with CHANGELOG.md's [Unreleased] section updated in the same commit as the change it describes.

Pushing to origin deploys to production

origin/main auto-deploys via Vercel. There is no separate staging gate. Never push without asking first, regardless of how routine the change looks.

npm run release (via commit-and-tag-version) reads every commit since the last tag, bumps the version, and rewrites CHANGELOG.md automatically. It does not push. Preview with npx commit-and-tag-version --dry-run.
