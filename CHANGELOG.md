# Changelog

All notable changes to this project are documented here. Format loosely
follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), versions
follow [SemVer](https://semver.org/). This project is pre-1.0 (alpha) —
expect breaking changes between minor versions. Version bumps and this file
are generated by [commit-and-tag-version](https://github.com/absolute-version/commit-and-tag-version)
(`npm run release`) from Conventional Commits — see `CONTRIBUTING.md`.

## [Unreleased]

### Security
- **Plaintext passwords stored and exposed (CRITICAL, TKT-0135)**: `GET
  /api/users` and `GET /api/regforms` returned every account's real
  plaintext login password to any Management caller — confirmed
  live-exploitable in a red-team pass. Passwords are now scrypt-hashed
  (`lib/passwords.js`) on every credential-creation path, generated with
  `crypto.randomBytes` instead of `Math.random()`, and no longer returned
  by any GET response. All 54 existing live credentials were migrated to
  hashes via a one-time script, after a full DB backup. A stored password
  can now only be reset, never read back — the Accounts/Applications
  tables show a "reset to view" prompt instead of the old inline value.
- **Auth bypass via hardcoded fallback session secret (CRITICAL, TKT-0134)**:
  `lib/session.js` no longer falls back to a hardcoded, known secret when
  `SESSION_SECRET` is unset — a red-team pass confirmed this let anyone
  forge a valid Management session/API-key token with zero credentials.
  Production now refuses to start without a real `SESSION_SECRET`;
  development generates a fresh random one per process instead.

### Changed
- **Billing pass, decluttered**: the search/status filter bar on the
  Invoices and Paychecks tables now starts collapsed behind a small
  "Filter" toggle instead of sitting on the page at all times, per user
  direction (less text, more breathing room) after the first version was
  reviewed.

### Removed
- **Billing pass, bulk send**: the "Send N drafts" bulk-action button (added
  earlier in this same pass, then relocated out of the crowded person
  header into the expanded view) removed entirely per user direction.
  Sending a single invoice/paycheck via its own row-level Send button is
  unaffected.

### Added
- **Billing pass, dashboard techniques**: 4 more changes on the Billing tab,
  applying Gorgilli 2025's interactive-filtering/bulk-action techniques and
  Seckler et al. 2014's post-submit confirmation guideline. (1) A search box
  and a status filter (Draft / Sent, unpaid / Needs approval / Settled) on
  both the Invoices and Paychecks tables, previously the only way to find
  "who hasn't paid" was expanding every single person by hand. (2) A "Send
  N drafts" bulk button on each person's collapsed accordion header,
  previously sending required expanding a person and clicking Send once
  per invoice/paycheck. (3) An on-demand hover reveal of the FX rate used
  on any INR Amount in a foreign currency, derived from the row's own
  Amount/INRAmount, no backend change. (4) Create Invoice and Create
  Paycheck now show an on-screen confirmation after a successful submit,
  previously the form just cleared silently with no sign anything
  happened.
- **Visual audit, Billing pass**: 7 UX changes grounded in three cited
  papers (progressive disclosure, form-guideline usability, dashboard
  cognitive load, see the earlier planning discussion). (1) Replaced
  `window.confirm()` at every delete site (Service, Enrollment, Invoice,
  Paycheck) with a themed inline two-step `ConfirmButton`, and added the
  same confirm step to Guide deletion, which previously had none at
  all. (2) Added a one-line "Use for:" hint to each of the four Billing
  action cards (Generate Drafts, Rebuild Drafts, both manual forms),
  which previously gave no guidance on which one applies to which
  situation. (3) Kept the currency label visible while editing a line-
  item amount, instead of it disappearing mid-edit. (4) Collapsed the
  Generate Drafts skipped-item list (previously one long unreadable
  comma-joined sentence) behind a "show details" toggle. (5) Added a
  per-person status summary (draft/unpaid/needs-approval counts) to the
  collapsed accordion header on both billing tables, previously zero
  signal until every person was individually expanded. (6) Moved
  Save/Cancel for editing INR Due next to the input itself, previously
  three columns away in a disconnected Actions column. (7) Dropped the
  redundant "INR " prefix from the INR Amount/INR Due cells now that the
  header already names the (always-fixed) currency, cutting repeated
  text across every row.
- **Visual audit, Billing pass, design direction**: bigger headings and
  more breathing room on the four Billing action cards (larger card
  titles, a colored left-accent border per card so the four are visually
  distinct at a glance, more vertical spacing between them). Trimmed
  each card's calculation/method paragraph down to one line, with the
  full detail moved to a hover tooltip on a dotted-underlined "How
  amounts are calculated" / "Details" label instead of always sitting on
  the page. Gave the two top-level billing tables (Invoices, Paychecks)
  their own `.billing-table` CSS class with more row padding and
  slightly larger text, scoped so every other, denser table in the app
  is untouched.
### Fixed
- **`DELETE /api/guides`**: returned 200 and looked like it worked, but
  never actually removed the record. `writeDB()` only upserts rows still
  present in the array it's given, it can't remove a row that's missing
  from it, so filtering the in-memory array and calling `writeDB` (this
  route's old delete path) silently no-opped against the database while
  the API response and the UI both looked correct. Switched to
  `deleteRecords()`, this app's real delete path, used everywhere else a
  record is actually removed. Found while testing an unrelated UI change
  (a new confirm-before-delete component); verified live: the record
  is now actually gone from the database after deleting.
- **Visual audit**: the Create Service form's per-Rate "restrict to a
  Group" select (nested Batch editor) had no label at all and its own
  text ("Any of the above") was clipped by a width too narrow for it.
  Added a label matching the form's own convention and widened the
  select so the full option text renders. Audited every Management tab
  (Applications, Pipeline, Accounts, Services, Schedule, Enrollments,
  Billing, Guides, Tickets, Audit Log) for real positioning issues;
  everything else checked out (the Accounts tab's wide tables are
  already correctly scoped to their own horizontal scroll, no page-
  level overflow). Same navy/gold style, no gradients/animations added,
  per this project's established convention.
- **TKT-0122**: three related bugs in Staff (and any role-based Service)
  enrollment, all one root cause. The client's rate-list computation
  required a Batch to exist before showing any rates, but a role-based
  Service (Staff, Ambassador, etc.) has no Batch at all, its Rates live
  directly on the Service, which `lib/billing.js`'s `ratesOf()` already
  handles correctly. So: the Rate dropdown was always empty for Staff
  (nothing to pick), a newly-added custom rate could never show up in
  that always-empty list either (though it did save correctly), and
  separately, whenever `rateId` was left blank the server silently
  defaulted to whichever rate sorted first, a real billing amount
  applied with no explicit choice behind it. Fixed the client to stop
  gating on a Batch, added an explicit "Select a rate…" placeholder so
  nothing is ever silently pre-selected, and closed the same gap
  server-side in `POST /api/enrollments` (`resolveRate` now requires an
  explicit, valid rateId instead of defaulting). Same fix applied to
  both the enroll form and the enrollment edit row. Verified live: a
  Staff enrollment with no rateId is now rejected server-side with a
  clear error; the Rate dropdown for a real Staff service now correctly
  shows its rate as a selectable option instead of nothing.
- **TKT-0109**: `GET /api/attendance?scheduleItemId=X`'s `roster` field was
  already trimmed to hide a Teacher/Student's same-type peers (TKT-0073),
  but the `attendanceItems` field sent alongside it was NOT, it stayed
  every record for the session regardless. `SessionAttendance.jsx` only
  ever renders a record for someone still in `roster`, so nothing
  visibly showed in the UI, but the raw API response still carried a

  devtools. Scoped `attendanceItems` to the same trimmed roster.
  Management's own view is untouched (still gets everyone, by design,
  for oversight). Verified live: reproduced the leak first (a real
  classmate's attendance record present in the raw API response),
  confirmed it's gone after the fix, confirmed Management still sees
  everything.

### Fixed
- **TKT-0097: a real, reproduced race condition in `POST /api/attendance`.**
  The "already logged" duplicate check read a snapshot via `readDB()` at
  the start of the request, then wrote at the end. Two near-simultaneous
  requests for the same (session, subject, author) could both read
  before either wrote, so both passed the check and both inserted.
  Reproduced live via a fast double-click and again with 5 truly
  concurrent requests before the fix (2 and 5 duplicate records created).
  An application-level re-check only shrinks the race window, it never
  closes it, so the fix is a new atomic Postgres function
  (`insert_attendance_if_new`, `data/tmp/migration_atomic_attendance_insert.sql`)
  that does the existence check and insert as one `INSERT ... WHERE NOT
  EXISTS` statement, the same category of fix as `increment_counter()`
  earlier this project. Verified live: 5 truly concurrent requests for
  the same person now correctly produce exactly 1 record and 4
  rejections (down from 5 successful duplicate inserts before), a
  different person logging normally afterward still works.
- **TKT-0090**: the payment-proof file picker in the student mark-paid
  flow (`InvoicePaidControl`) was a bare native file input: raw
  browser-default "Choose File" / "No file chosen" text, unstyled,
  with no context, next to a disabled "Confirm payment" button. The
  first pass added a label above it. User feedback on that fix said it
  wasn't enough; the native control itself still read as confusing
  browser boilerplate. Replaced it. The native input is now visually
  hidden and triggered by a real "Upload payment proof" button, with
  the chosen filename (or an explicit "none selected yet" prompt,
  styled like the rest of the app) shown next to it. Verified live on
  a real invoice.
- **TKT-0094**: attendance create and edit never showed up in the audit
  log, only delete did. Added `logAudit()` calls to both `POST`
  (create) and `PATCH` (mark correct / edit, TKT-0095) in
  `app/api/attendance/route.js`, matching the pattern already used for
  delete. Edit entries show the before → after Status/hours change.
  Verified live: created and edited a real disposable attendance
  record, confirmed both actions now appear in the audit log with
  correct summaries.
- **TKT-0091**: the Trial dashboard's "Mark as paid" button called
  `PATCH /api/invoices` with `status: "Paid"` directly, a
  Management-only field, so the request was always rejected when a
  real Trial account (not Management) called it. The invoice's Status
  could never actually change. Switched to the same self-report-then-
  Management-confirms pattern the Student dashboard already uses
  correctly (`studentPaidFlag` + a payment-proof upload via
  `InvoicePaidControl`), the established correct behavior per TKT-0089.
  Verified live end-to-end with disposable data: the old direct-status
  call still correctly rejects with "Management only." (that field
  stays Management-only, by design), the new self-report call
  succeeds and stamps `StudentPaidFlag`/`PaidAt` correctly.
- **TKT-0084, performance: Activate/Deactivate (and every other single-
  field account edit) still took ~2s after the TKT-0081 read cache**,

### Fixed
- **Critical: concurrent writes to the same collection could silently
  delete each other's records.** `sync_table()`, used by every `writeDB()`
  call, deleted every row NOT in the calling request's in-memory snapshot
  before upserting. Two concurrent requests writing the same collection
  each read the table before the other's insert landed, so each snapshot
  excluded the other's new row, and whichever write ran last deleted the
  other's record. Reproduced live: 8 concurrent ticket creations left only
  1 of 8 behind. Fixed with a new Postgres function, `upsert_rows()`
  (insert/update only, never deletes; data/tmp/migration_incremental_writes.sql,
  applied to production), plus a new `deleteRecords()` export for the
  handful of routes that actually remove records (apikeys, services,
  enrollments, invoices, paychecks, and both migrate-monthly merges),
  which now target only the exact ids being removed instead of relying on
  writeDB to infer deletions from what's missing off a snapshot. Verified
  live: the same 8-concurrent-request test now leaves all 8 records
  intact; a mint-then-delete round trip on a real record confirmed the
  explicit delete path still actually removes it from Postgres.
- **Id minting raced under concurrency too, hitting production twice**
  (paychecks, attendanceitems; Sentry: "ON CONFLICT DO UPDATE command
  cannot affect row a second time"). `nextId()` incremented `db.counters`
  purely in memory, so two concurrent requests could read the same
  counter value before either wrote it back and both mint the identical
  id. Fixed with a new Postgres function, `increment_counter()`
  (data/tmp/migration_atomic_counter.sql, applied to production). The
  read-and-increment now happens as one atomic UPDATE, so concurrent
  callers are serialized by the database itself instead of racing on
  JS-level state two separate serverless invocations can never share.
  Every `nextId()` call site across `app/api` was updated to `await` it.
  Verified live: 8 concurrent requests now mint 8 distinct ids with zero
  conflicts. Found via a Sentry review that also surfaced the
  collection-wipe bug above. Both share the same root cause: deriving a
  write from a stale in-memory snapshot instead of a database-atomic
  operation.
