## [Unreleased]

### Fixed
- **mcq-digitizer's QP-side boundary detector silently dropped a real
  question whenever its own heading line was artificially short**, found
  by a corpus-wide audit built specifically to test for pairing/counting
  errors: cross-checking every paper's own detected max question number
  against its mark scheme's own independently-detected max, which should
  always agree even when the exact count doesn't. 37 of 186 papers
  disagreed. Root cause: a length floor exists on the bare "N text"
  heading form specifically to reject short numeric-table-fragment false
  positives (documented already, e.g. a force-diagram's "45 N" label) --
  but it was checked against a heading's OWN FIRST LINE ALONE, and
  isotope/nuclide notation (a superscript mass number and subscript
  atomic number rendering as their own tiny text fragment, e.g.
  "222/86Rn") or plain word-wrap can leave a real question's first line
  far short of that floor even though the full stem clearly isn't short
  once its own following lines are included ("42 The 1H3" -- real
  content continues "+ ion was first characterised..."; "7 The isotope"
  -- continues across 5 more short fragments before reaching "What is
  the number of stages..."). Fixed with `_stem_with_continuation`: merges
  a heading's own following lines (bounded, up to 8) into the length
  check, stopping the moment a line looks like a new heading, a bare
  digit, an option letter, or -- critically -- the start of a brand new
  complete capitalized sentence of its own. That last guard exists
  because an earlier version of this fix, without it, reintroduced the
  EXACT original "45 N" false positive it was meant to avoid (the line
  after "45 N" is a genuine new sentence belonging to a DIFFERENT,
  already-open question, not a continuation of "45 N" at all -- a real
  continuation never starts a fresh capitalized sentence, it continues
  mid-clause). A second, narrower regex (capital letters only, not the
  broader class that also allows "(" for genuine parenthetical-opening
  questions) was needed for this specific guard after it wrongly blocked
  one more real recovery, a chemical equation continuation that happens
  to start with "(". Verified against 9 real cases (5 recoveries across
  4 distinct papers, the original "45 N" regression, the "(" collision)
  plus both baseline files. Full corpus regression: 171/186 papers
  unchanged, 15 papers recovered real previously-invisible questions
  (one paper alone, CAIE A Level Physics "Ch11 Particle Physics"
  Worksheet 1, recovered 5), 0 duplicate question numbers, 0 corrupt
  images, 0 exceptions anywhere in the corpus.

  A separate, distinct cause of the same symptom was found by the same
  audit but is NOT fixed by this change and needs its own investigation:
  a bare question number completely ALONE on its own line (e.g. CAIE
  IGCSE Biology "Ch17 Inheritance" Q11/Q15), a different code path
  (`QUESTION_BARE_ALONE_RE`) with its own separate "is the next line a
  real sentence" gate that this fix doesn't touch. ~14 of the original 37
  audit mismatches remain open for this reason.

  A follow-up pass found the one-line extension above wasn't always
  enough: heavier nuclide notation can wrap a real stem across many short
  fragments in a row (confirmed real, CAIE A Level Physics "Ch11 Particle
  Physics" Worksheet 1 Q7: "The isotope" / "Rn" / "decays in a sequence
  of emissions to form the isotope" / "Pb." / "At each stage" / "of the
  decay sequence..." before finally reaching a real sentence long enough
  to clear the floor on its own). `_stem_with_continuation` now merges up
  to 8 of a heading's own following lines, not just one, with the same
  stop conditions. That same paper alone recovered 5 previously-invisible
  questions once multi-line merging was in place, versus 2 with the
  single-line version.

  Multi-line merging introduced one more real false positive of its own,
  caught before shipping: chaining together several short, individually
  harmless cover-page metadata labels ("MS" + "Level:" + "A Level" +
  "Subject:"...) can coincidentally clear the length floor even though
  none of them, alone or as a "new capitalized sentence," would --
  inventing a phantom "question 1" pointing at this tool's own
  DivergenCIE cover page (CAIE A Level Physics "Ch1 Measurement
  Techniques" Worksheet 1's own MS, whose title wraps as "...Worksheet" /
  "1 MS"). Fixed with one more stop condition: never merge across a
  "Field:"-style label line, since a real question's own wrapped
  continuation is never a bare field label on its own line. Full corpus
  regression after both follow-ups: 0 duplicate question numbers, 0
  corrupt images, 0 exceptions anywhere in the corpus; the field-label
  fix alone changed 0 QP-side question counts (as expected -- it only
  ever affected an MS-side cover-page artifact, never real content).
- **mcq-digitizer's MS answer-resolution missed two real, explicitly-stated
  answers**, found by individually auditing every one of the 23 questions
  the live database still couldn't auto-grade rather than assuming they
  all shared one cause. (1) A decorative bullet glyph a source PDF's font
  renders before explanation lines -- sometimes a real Unicode checkmark,
  sometimes a raw Private-Use-Area codepoint (confirmed real: U+F0FC in a
  Wingdings-style embedded font) -- was glued directly onto a real question
  number with no separating space ("2.  The diagram shows..."). Every
  heading regex in this file requires a line to START with a digit, so the
  leading glyph silently defeated every one of them: the question was
  entirely invisible to boundary detection, not just unresolved (CAIE
  IGCSE Biology "Human Nutrition" Worksheet 1 Q2). Fixed by stripping this
  class of leading decorative glyph at text-extraction time, before any
  heading regex ever sees the line. (2) A distinct real answer phrasing
  this tool never recognized: "Cell A can be recognized as a palisade
  mesophyll cell..." (CAIE IGCSE Biology "Plant Nutrition" Worksheet 1
  Q12) states the answer explicitly and unambiguously, but doesn't match
  the existing "X is correct"/"X is the correct answer" pattern. Added a
  second pattern recognizing "X can be recognized as". Together these
  recovered 2 of 23 previously-unresolved questions with zero risk to
  every other resolved answer, since both changes only add new matches,
  never remove or reinterpret existing ones. Full corpus regression:
  186/186 papers' question counts unchanged, 0 duplicate question
  numbers, 0 corrupt images, 0 exceptions; both baseline files unchanged.
- **mcq-digitizer split one real Section B question into a truncated
  original plus a phantom duplicate under the wrong number**, found
  while individually auditing every unresolved question in the live
  database rather than assuming a pattern from a sample. The real
  question was CAIE IAL Chemistry "2.2 Atomic Structure" Q25, about the
  isotope cobalt-60 written as a superscript-60-over-subscript-27
  nuclide notation. The bare "27" (the atomic number, rendered at 9pt --
  small enough to pass as a real heading candidate, the same size class
  as a genuine footer number or a chemical-formula subscript) isn't a
  horizontal ruler tick-mark row (`_is_tick_row` only catches siblings
  at nearly the SAME y-position) since it's stacked vertically under the
  mass number instead, so nothing rejected it. Root cause once traced
  down: the heading detector's "is the next line a real sentence"
  check tries both raw-text-stream order and y-position order and
  accepts either (`any(...)`, not `all(...)`) -- deliberately, per an
  earlier fix for a real file where only one order matched. Raw order
  correctly showed this "27" sits mid-sentence (fails the check); but
  position order, sorting purely by y-coordinate, happened to land the
  very next line on a completely unrelated real sentence further down
  the actual question ("Which statements about an atom of cobalt-60 are
  correct?"), passing the gate by coincidence. The truncated "Q25" lost
  its own three numbered statements entirely; "Q27" was a duplicate of
  the same content under the wrong number, with two knock-on effects:
  it inflated the paper's own question count by one, and it made the
  real Q25 permanently unresolvable against its mark scheme, which
  naturally has no separate answer for a "Q27" that was never a real
  question. Fixed with a new `_is_stacked_notation` check recognizing
  this specific vertical-stack shape (another bare 1-2 digit line of
  the same reduced size directly above, within one line height) as
  nuclide notation, not a heading. Verified: the paper now renders as
  one complete, un-split Q25 with all three statements and no phantom
  27th question; both baseline files unchanged; full corpus regression
  found exactly one paper's question count changed (this one, 25 -> 24,
  the phantom's removal) with 0 duplicate question numbers, 0 corrupt
  images, and 0 exceptions anywhere else in the 186-paper corpus.
- **mcq-digitizer's MS answer-resolution pipeline was blind to any
  question whose real options are a raster-image answer table (an
  infographic-style layout with no extractable A-D text) -- the
  dominant cause, by far, of "this question's mark scheme wasn't clear-
  cut enough to auto-grade" in the live app (74 of 87 unresolved
  questions in one full audit).** Root cause: `find_question_starts`'s
  option-proximity gate (added earlier to reject a coincidental
  digit+sentence match, like a stray "69 Time Allowed" on a cover page)
  only ever accepted a candidate heading if a plain-text "A"/"B"/"C"/"D"
  line showed up nearby -- but a raster-image answer table has none, so
  a perfectly real, sentence-shaped numbered question right next to one
  failed the gate and the WHOLE question vanished from the pipeline
  entirely, not just its answer. Fixed by accepting an embedded image
  block nearby as equally valid evidence of a real question, alongside
  the existing text-based check. Verified directly against the real
  source PDF: a previously invisible question (with its answer plainly
  circled in the image, e.g. "ANSWER C IS CORRECT") is now correctly
  detected and handed to the lightweight-icon/Gemini resolution chain
  that can actually read it. This also recovered entire TRAILING
  questions that had no detected boundary at all in 13 real papers
  (each visually verified against the real source PDF, e.g. two
  genuine, previously 100%-invisible questions at the end of a 30-
  question Biology paper) -- all recoveries, zero regressions: 0
  duplicate question numbers, 0 corrupt/malformed images, 0 question-
  count decreases anywhere in the corpus, both baseline files
  unchanged.
- **mcq-digitizer spuriously split real questions in two, cutting one
  question's real options out of its own crop entirely and attaching
  them to a bogus extra "question."** Found by the user directly, live
  on the deployed app: a ruler/diagram's own scale-label numbers (a
  large, bold "2" on a cm ruler, real extractable text at 18pt --
  comfortably clearing the existing size>=9 floor, which only ever
  guarded the OPPOSITE direction against a small page-footer number)
  got accepted as a genuine second question-start digit. The real
  question got chopped in half: the first half showed only the diagram
  truncated right at the ruler with zero answer options, and the second
  half re-showed part of the ruler followed by the real options that
  belonged to the first half all along -- visibly broken in the live
  UI, exactly as reported. Root cause: unlike a page-footer number,
  which is reliably small, a ruler/table tick-mark number can be ANY
  size, so no size threshold alone can separate the two cases. Fixed
  with a shape-based signal instead: a bare 1-2 digit line with 2+ OTHER
  bare-digit lines at nearly the same y-position (a horizontal row of
  tick labels like "1 2 3") is tick-mark/table noise, never a real
  heading, regardless of size. Verified via direct visual comparison
  against the real source PDF page (not assumed): the previously-broken
  question now renders as one single, complete, correct crop with all 4
  real options. A second, separately-reported defect from the same live
  session (a large blank gap inside a different question's crop) turned
  out to be the exact same root cause on a different ruler diagram in
  the same paper -- fixed by the same change. Regression-verified
  across the full real corpus: 0 changes to any other paper's detected
  question count (186/186 unchanged), 0 new duplicates, 0 new corrupt
  images, both established baseline files unchanged.
- **mcq-digitizer lightweight icon-detection could produce an
  out-of-range answer letter ("E") for a 4-option question.** Found by
  red-teaming the ACTUAL produced database.json + saved crop images
  after a full library rebuild, not just the parsing logic: 2 real
  questions had `correctAnswer: "E"`, traced to `lightweight_detect.py`
  mapping a green mark's rank directly to a letter (`chr(65+idx)`) with
  a "plausible" bound that allowed up to 5 total marks -- one too many
  for a tool that only ever supports A-D. This is a regression of a bug
  the code's own comments already claimed to have fixed once before (an
  earlier real case: unrelated red diagram elements produced extra
  blobs); the previous fix capped the bound at 5, not 4, so the same
  failure mode recurred. Fixed the bound itself and added a second,
  independent `idx < 4` guard at both call sites (`build_full_database.py`,
  `resolve_ambiguous.py`) so this can't silently regress a third time.
  Also fixed a real schema drift in `build_full_database.py`, found via
  a smoke test before the rebuild: it still expected `parse_qp`'s old
  `images` (plural list) shape from before this session's crop-
  stitching consolidation to a single `image` field -- would have
  KeyError'd on the very first paper of a real rebuild. Full library
  rebuild (186/196 papers, 5125 questions) re-verified clean after the
  fix: 0 answers outside A-D, 0 missing/corrupt/blank/tiny/malformed
  crop images, only 1 remaining "answer not among detected options"
  case (the already-documented out-of-scope 1/2/3-statement question
  format, not a bug).
- **mcq-digitizer question/answer content hardened against a red-team pass
  focused on the actual QP/MS pairs, crops, and grading -- not just server
  behavior.** Found and fixed 3 real correctness/quality bugs by
  deliberately attacking real content, not just re-confirming known-good
  files: (1) some real papers put an option's letter and its answer text
  on ONE merged line ("A X has a larger thermal capacity than Y.")
  instead of the letter alone -- `optionLetters` silently came back
  missing options (confirmed real: `['D']` for a question with 4 real
  choices), meaning the quiz UI rendered too few clickable answer
  buttons; (2) a chemical structure diagram's element-symbol lines (H, C,
  O each alone on their own line) got misread as MCQ option-letter
  markers by the same regex, feeding a completely spurious "resolved"
  answer into the mark-scheme elimination logic for a block with no real
  answer-key content at all; (3) the most severe: any question whose
  options/diagram/table is an embedded raster image rather than text
  (confirmed real and common -- CAIE-style row/column answer tables are
  frequently rendered as images) had its crop silently truncated right
  after the last detected TEXT line, cutting the actual options out of
  the image the student sees entirely, even though `optionLetters` often
  still reported a plausible-looking (but synthetic default) A-D set.
  Fixed by scanning for embedded image blocks within each question's own
  page range and extending the crop to cover them. A dedicated corpus
  sweep across all 186 locally-available real QP files found 88 crops
  with visibly-implausible (<1:15 aspect ratio) proportions before this
  fix; a full pass with the fix applied plus two follow-on fixes for
  narrower boundary-detection false positives it surfaced (a stray
  diagram digit and a stray force-diagram label each wrongly promoted to
  a "question start", truncating the real question before them) brought
  that to 0. Both established baseline regression files (Physics Ch1.1,
  Enzymes) re-verified unchanged after every step.

  A follow-up pass closed most of what the above left open. Rather than
  add OCR/LLM to read letters out of pixels, `parse_qp` now reuses the
  same embedded-image detection the crop fix already computes: if a
  question's own range contains a raster image, its options almost
  certainly live inside that image, so no partial text match can be
  trusted there at all -- `optionLetters` now falls back straight to the
  full default set instead of risking a wrong-but-plausible-looking
  partial one (confirmed real before this: `['A']` for a question whose
  actual answer was C, from a stray diagram label). Questions where the
  resolved MS answer wasn't even among the QP's own detected options
  dropped from 41 (before any of this round's fixes) to 19.

  A second follow-up found one more real layout: some real files put
  each option's VALUE on its own line with the NEXT option's letter
  trailing at the end of it ("0.5 %           B", "0.8 %           C",
  ...) instead of the letter ever starting a line of its own -- confirmed
  real on CAIE A Level Physics Ch1 "Measurement Techniques" Q44, where
  only the first, isolated "A" was ever found. A new trailing-letter
  pattern requires a wide (>=3 space) gap before the letter specifically
  to tell this apart from a genuine physics unit symbol following a
  measurement with one natural space ("50 A" for amps, similarly
  N/V/W/J...) -- the real column-alignment gap measured on the confirmed
  case is 11 spaces, nothing like a natural unit separator. Questions
  where the resolved MS answer wasn't even among the QP's own detected
  options dropped further, from 19 to 6.

  Investigating those final 6 individually found two distinct causes.
  Two of them (CAIE IGCSE Chemistry "Property of Metals" Q4, CAIE A
  Level Physics "Uniform Electric Fields" Q17) were a THIRD real crop-
  truncation cause: a diagram drawn with PDF vector paths (field lines,
  atom circles) rather than text or a raster image -- invisible to both
  extract_lines (text-only) and image_block_bottom (raster-only), since
  PyMuPDF exposes vector paths through a completely separate API
  (`page.get_drawings()`). A new `drawing_block_bottom` mirrors
  `image_block_bottom` for this case and feeds the same optionLetters
  safe-default fallback. The other 4 turned out to be a genuinely
  different, out-of-scope question format this tool has never supported
  (CAIE's "which of the following statements 1/2/3 are correct"
  multi-response style, not standard lettered A-D options) -- confirmed
  by reading the actual crops, not assumed; a couple of them only looked
  like option-letter false positives because a chemical equation's
  element symbols ("C (graphite) -> C (diamond)") are structurally
  indistinguishable from a real merged option line by a local regex.
  Left alone rather than built out, matching this tool's existing
  Section-B-style scope boundary. Net result across the whole real
  corpus (5125 questions): questions with a non-4 option count went from
  91 (start of this whole investigation) to 2; MS answers not among
  their own QP's detected options went from 41 to 1 -- the one
  remaining case is the out-of-scope statement format above, not a bug.
- **mcq-digitizer server hardened against a red-team pass of adversarial
  requests.** Found and fixed 3 real server bugs by deliberately attacking
  the live HTTP server, not just the parser: (1) a corrupted
  `drive-map.json` crashed the *entire* process, not just that request --
  `/api/library`'s success path called `res.writeHead(200, ...)` before
  the JSON body that could throw was computed, so the failure's own
  `catch` block tried to write a second header on an already-sent
  response and Node's uncaught `ERR_HTTP_HEADERS_SENT` took the whole
  server down; fixed by computing the response body fully before writing
  any headers; (2) uploading non-PDF bytes as `qpBase64`/`msBase64`
  returned a 500 with a full Python stack trace -- including local
  filesystem paths -- straight in the HTTP response; now returns a clean
  400 with a generic message; (3) a request body over the 40MB limit
  called `req.destroy()` before any response was written, so the client
  just saw a connection reset instead of an error; now returns a clean
  413. Malformed/empty JSON bodies also now return 400 instead of 500
  with a raw `JSON.parse` error message. All fixes verified against the
  live server with the exact adversarial requests that found each bug,
  plus a full regression pass of 11 adversarial cases together. A
  separate corpus-level sweep (duplicate question numbers, corrupt/tiny
  images, invalid option-letter sets, zero-option questions) across all
  186 locally-available real QP files found 0 issues.
- **mcq-digitizer's new Section B detection (above) wrongly attached the
  statement-format key to ordinary lettered MCQs, reported live by the
  user on several real ruler/diagram questions.** Root cause: a
  ruler/graph's own axis tick-mark labels ("0 1 2 3 4 5...") render as
  a run of bare single-digit lines at the same size as real content,
  an indistinguishable shape from the genuine "1"/"2"/"3" statement
  markers the new detector was built to find. Fixed with two
  independent signals verified against every real reported case: (1)
  a same-size bare "4" disqualifies the whole match, since a real
  statement question never has a fourth numbered line but a ruler
  reliably does; (2) real A-D options found within the detector's own
  boundary-scoped window disqualify it too, since a statement question
  never prints A-D on its own page. A second, separate defect
  (unrelated to Section B) was found and fixed in the same pass: an
  over-eager `Section [A-Z]` prefix match meant to detect real exam
  section breaks also matched physics diagram labels like "section X
  of dam" mid-question, truncating that question's crop right after
  the label -- narrowed to a whole-line match. A third, self-inflicted
  defect surfaced only under full regression: a statement question's
  own continuation markers ("2", "3") were being independently
  re-evaluated by the main scan and wrongly reclassified as boundary
  markers in their own right, truncating the very question they
  belonged to -- fixed with a cleanup pass that un-marks any such
  boundary sitting strictly inside a confirmed statement question's own
  range. A fourth defect, found by widening the corpus sweep rather
  than by a user report: the same lookahead window used to look for
  nearby A-D options (30 lines) was too short for any question whose
  own diagram prints many separate short numeric lines before its real
  options -- a wave graph's x-axis tick labels, an isotope table's
  proton/neutron/electron counts -- pushing genuine options past the
  window and dropping the whole question. Widened to 55 lines,
  recovering 3 more previously-invisible real questions across the
  corpus. All four fixes verified against every real case reported or
  found in this round (16 known cases total, spanning rulers,
  stopwatches, dams, isotopes, chemical fractions, and the wave-graph/
  ionic-table cases the window fix specifically recovered) plus both
  established baseline files; full corpus regression after all four
  fixes: 184/186 papers' question counts unchanged, the 2 remaining
  changes both confirmed genuine recoveries by direct visual
  comparison against the real source PDF, 0 duplicate question
  numbers, 0 corrupt/malformed images, 0 MS-side exceptions.
- **mcq-digitizer heading detection no longer depends on font size.** A
  24-file random sample across all 5 real subjects found font size
  doesn't generalize at all (one real file has headings *smaller* than
  its own body text) -- dropped the size/bold gate for the punctuated
  "N." form, added a validated bare "N text" form (no punctuation),
  widened MS answer-phrasing coverage ("X is the correct answer", "X
  is/are therefore incorrect"). Result: A Levels Chemistry/Biology/
  Physics went from ~0% (undetected) to 100% auto-graded; grand total
  across the sample rose from a scattered mix to 80% (622/778). Full
  before/after account in `prototypes/mcq-digitizer/README.md`.

### Added
- **mcq-digitizer now supports CAIE's "Section B" / "multiple
  completion" question format** (one or more of three numbered
  statements 1-3 may be correct; A-D select a fixed combination),
  previously wrongly treated as out of scope. This format never prints
  A-D on the question page itself -- the combination key is stated
  once, in the section's own instructions, before the whole block of
  questions -- so a bare numbered-statement stem was indistinguishable
  from a coincidental false match and got suppressed to a boundary-only
  marker, not a real question. Confirmed the exact key is fixed and
  universal directly from a real paper's own instructions text (not
  assumed): A = 1,2,3 correct; B = 1,2 only; C = 2,3 only; D = 1 only.
  Detected via a reliable shape signature (2+ bare "1"/"2"/"3" lines
  near the stem) and the fixed key table is now rendered once and
  stitched onto every such question's own crop, so it reads as a
  complete, self-contained, gradable question; `optionLetters` is
  forced to the real A-D set instead of the default. The mark-scheme
  side needed no changes at all -- it already records the response
  letter directly (e.g. "23. D"), which the existing direct-answer fast
  path already resolves correctly. Impact was much larger than
  expected: this is apparently the dominant question style in large
  parts of the A Level Chemistry library -- one paper's real question
  count nearly doubled (19 -> 38) once no longer wrongly suppressed.
  Verified per-question against real source PDFs and against the
  MS-resolved answer for several cases across multiple different
  papers; regression-checked across the full corpus (0 duplicate
  question numbers, 0 corrupt images, both baseline files unchanged).
- **mcq-digitizer's library flow (`/api/fetch-and-digitize`) now serves
  straight from the pre-built full-library database**
  (`data/mcq-digitizer/full-library/database.json` + saved crop images)
  when a paper is already in it, instead of re-downloading and
  re-parsing the same PDFs live on every single request. ~40x faster in
  practice (0.24s vs 9.8s for a real 16-question paper) and more
  complete: the database carries every answer the offline batched-
  Gemini/lightweight fallback chain resolved, not just what plain MS
  text-parsing plus the answer-cache can find live. A paper NOT in the
  database (the small number of real download/pairing failures --
  see `failures.json`) transparently falls back to the previous live
  download-and-parse path, unchanged.
- **mcq-digitizer library mode**: browse a picker (Board → Subject →
  Category → Paper) built from a pre-built local JSON map of
  DivergenCIE's own Drive (`data/mcq-digitizer/drive-map/`, 428 files /
  196 QP+MS pairs across IGCSE and A Levels), instead of manually
  uploading files. No live Google Drive API/MCP call from the server --
  picking a paper triggers a plain HTTPS download of just that pair by
  its public Drive link, then digitizes it the same way as a manual
  upload. QP/MS pairing handles real, inconsistent Drive filenames via
  stopword-filtered token-set matching (95%/186/196 paired correctly
  library-wide). Manual upload kept as a fallback.

### Changed
- **mcq-digitizer rebuilt around image-cropping + elimination-based answer
  inference**, after real-world testing against an actual CAIE IGCSE
  Biology MCQ paper (pulled from DivergenCIE's own Drive) showed the
  original plain-text option-parsing design found 0/40 questions: real
  options are often diagrams/tables, and this MS never states an answer
  directly, only which letters are wrong. Per explicit "no OCR" direction,
  each question is now cropped as a verbatim image instead of re-typeset;
  the correct answer is inferred by elimination when the MS's explanation
  narrows to exactly one remaining letter, and left ungraded (never
  guessed) otherwise. Result on the real file: 40/40 questions found,
  26/40 (65%) confidently auto-graded. See
  `prototypes/mcq-digitizer/README.md` for the full account.

### Added
- **MCQ Digitizer prototype** (`prototypes/mcq-digitizer/`): standalone
  tool that turns a Multiple Choice Question paper + its Mark Scheme into
  an instant, auto-graded interactive quiz. Both PDFs are required
  upfront (no generate-MS mode). Fully rule-based, no LLM anywhere — not
  even for grading, which happens entirely client-side in the browser —
  a genuinely simpler category than `exam-grader`/`quiz-digitizer`, since
  matching a selected letter to an answer key needs no judgment. No API
  key, no `.env`, no OpenRouter dependency. Verified live: self-authored
  5-question sample digitized correctly via a real running server,
  missing-field validation and static file serving both confirmed.
- **Management dashboard, non-invasive UX audit pass**: grounded in this
  project's own UX study notes, reusing only established patterns
  (`BillingFilterBar` search, `.num` tabular-nums, `.subject-truncate`
  ellipsis, `.scroll-fade` scroll hint) rather than introducing new ones.
  Enrollments: search box, right-aligned Rate/Start/End, Service-name
  truncation, scroll-fade on the list. Applications: search box.
  Pipeline: Service-name truncation on Trial/Interview/Pending tables,

### Performance
- **DB read-cache TTL: 2s -> 30s**: `readDB()`'s in-process aggregate cache
  is invalidated immediately and unconditionally on every write (confirmed
  by reading `writeDB()`), so the old 2-second TTL never actually bounded
  staleness after a real change — it only limited how long an *unchanged*
  read stayed cached. Under realistic browsing cadence most requests fell
  just outside that window and re-paid the full 0.9-3.4s DB aggregation.
  Raised to 30s: freshness after any real write is unaffected (still
  instant, live-verified with a real create-then-read and delete-then-read
  round trip), only the cost of unchanged repeat reads dropped —
  684ms -> 24ms average on `/api/me` under a realistic request-cadence
  benchmark, similar drops across every route. Accepted tradeoff: a write
  made by bypassing the app entirely (directly in the Supabase dashboard)
  could take up to 30s to be picked up — this project already has a
  standing rule against doing that.
- **`GET /api/schedule` payload deduplication**: `openPoolSlots` was a full
  second copy of nearly the same objects already present in `scheduleItems`
  (504 of 509 items duplicated, on real data). Now returns lightweight
  `openPoolSlotIds` instead; the one caller that reads it reconstitutes the
  full objects client-side from `scheduleItems`, which it already has in
  full. 317KB -> 165KB (-48%), measured live, same data, same UI behavior.
- **Schedule image caching + WebP**: `/api/schedule/image` and
  `/api/schedule/admin-image` sent `Cache-Control: no-store`, forcing a
  full canvas re-render and full re-transfer on every single dashboard
  view, even unchanged. Both routes now compute an ETag over the exact
  render inputs and honor conditional GET (304 on an unchanged repeat
  view — 0 bytes instead of 500KB+, confirmed live). The inline view is
  also now re-encoded as WebP (quality 90, via `sharp`) instead of PNG —
  visually indistinguishable for this kind of flat-color rendered chart,
  ~84% smaller (516KB -> 80KB measured). Downloads still get real PNG
  for maximum compatibility. Added `sharp` as an explicit dependency (was
  present only transitively via Next's own image tooling before).

### Security
- **Negative schedule slot duration accepted (LOW, TKT-0140)**: `POST
  /api/schedule` only guarded 0/NaN, not negative values. Now rejects
  any non-positive duration with 400.
- **Broken access control on Drive-folder listing (MEDIUM, TKT-0139)**:
  `GET /api/resources/drive-folder` accepted any Drive folder link/ID from
  any authenticated account with no ownership check. Now cross-checks the
  requested folder against the caller's own enrollments' Services, 403 on
  no match.
- **No file-type or size validation on payment-proof upload (MEDIUM,
  TKT-0138)**: `POST /api/invoices/mark-paid` took the uploaded file's
  extension and Content-Type verbatim from the client with no allowlist
  and no size cap. Now capped at 10MB with a jpg/jpeg/png/pdf allowlist.
- **No rate limiting on login or registration (HIGH/MEDIUM, TKT-0136,
  TKT-0137)**: `POST /api/login` allowed unlimited-speed password
  guessing (8 rapid wrong attempts, all instant 401, no throttle);
  `POST /api/register` allowed unauthenticated spam of the RegForm
  queue. Both now go through a shared in-process sliding-window limiter
  (`lib/rateLimit.js`, 5 attempts per 5 minutes), returning 429 once
  exceeded.
- **Plaintext passwords stored and exposed (CRITICAL, TKT-0135)**: `GET
  /api/users` and `GET /api/regforms` returned every account's real
  plaintext login password to any Management caller — confirmed
  live-exploitable in a red-team pass. Passwords are now scrypt-hashed
  (`lib/passwords.js`) on every credential-creation path, generated with
  `crypto.randomBytes` instead of `Math.random()`, and no longer returned
  by any GET response. All 54 existing live credentials were migrated to
  hashes via a one-time script, after a full DB backup. A stored password
  can now only be reset, never read back — the Accounts/Applications
  tables show a "reset to view" prompt instead of the old inline value.
- **Auth bypass via hardcoded fallback session secret (CRITICAL, TKT-0134)**:
  `lib/session.js` no longer falls back to a hardcoded, known secret when
  `SESSION_SECRET` is unset — a red-team pass confirmed this let anyone
  forge a valid Management session/API-key token with zero credentials.
  Production now refuses to start without a real `SESSION_SECRET`;
  development generates a fresh random one per process instead.

### Fixed
- **Critical: concurrent writes to the same collection could silently
  delete each other's records.** `sync_table()`, used by every `writeDB()`
  call, deleted every row NOT in the calling request's in-memory snapshot
  before upserting. Two concurrent requests writing the same collection
  each read the table before the other's insert landed, so each snapshot
  excluded the other's new row, and whichever write ran last deleted the
  other's record. Reproduced live: 8 concurrent ticket creations left only
  1 of 8 behind. Fixed with a new Postgres function, `upsert_rows()`
  (insert/update only, never deletes; data/tmp/migration_incremental_writes.sql,
  applied to production), plus a new `deleteRecords()` export for the
  handful of routes that actually remove records (apikeys, services,
  enrollments, invoices, paychecks, and both migrate-monthly merges),
  which now target only the exact ids being removed instead of relying on
  writeDB to infer deletions from what's missing off a snapshot. Verified
  live: the same 8-concurrent-request test now leaves all 8 records
  intact; a mint-then-delete round trip on a real record confirmed the
  explicit delete path still actually removes it from Postgres.
- **Id minting raced under concurrency too, hitting production twice**
  (paychecks, attendanceitems; Sentry: "ON CONFLICT DO UPDATE command
  cannot affect row a second time"). `nextId()` incremented `db.counters`
  purely in memory, so two concurrent requests could read the same
  counter value before either wrote it back and both mint the identical
  id. Fixed with a new Postgres function, `increment_counter()`
  (data/tmp/migration_atomic_counter.sql, applied to production). The
  read-and-increment now happens as one atomic UPDATE, so concurrent
  callers are serialized by the database itself instead of racing on
  JS-level state two separate serverless invocations can never share.
  Every `nextId()` call site across `app/api` was updated to `await` it.
  Verified live: 8 concurrent requests now mint 8 distinct ids with zero
  conflicts. Found via a Sentry review that also surfaced the
  collection-wipe bug above. Both share the same root cause: deriving a
  write from a stale in-memory snapshot instead of a database-atomic
  operation.
