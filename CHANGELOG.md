  tables (Invoices/Paychecks), same UI and functions throughout, no
  redesign. Fixed a real JSX whitespace bug in the duplicate-month
  warning banner, which silently rendered as "1 student/monthwith more

  was one generic link above the whole Invoices table, same fixed Stripe
  URL for every click regardless of which invoice or how much was owed.
  This app has no live Stripe API key, only a static fixed-price Payment
  Link, so the charged amount still can't be made correct without a real
  Stripe integration. Moved to a per-invoice "Pay online" link instead

  (single or multi-select) now rejects a $0 amount outright with a clear
  error, on both Invoices and Paychecks. Bulk "Generate Drafts" no longer
  creates a $0 line item for an enrollment with no scheduled hours (the
  config-gap case); it's skipped and reported in the summary message

  temporary state, not a config gap) is deliberately NOT blocked, so the
  usual generate-early-then-log-attendance-later workflow still works.
  Verified live: generating a real future month now correctly creates 0
  records and reports every skipped enrollment by name.

### Fixed
- **Critical: future-month invoices/paychecks silently billed $0 despite
  real logged hours.** `getRateToINR()` fetches the exchange rate for the
  1st of the invoice's/paycheck's own month, but a month that hasn't
  happened yet has no historical rate to fetch. Both API mirrors 404 on a
  future date, and that was treated the same as "rate genuinely
  unavailable": `INRAmount`, `INRDue`, and the derived `Amount` all
  silently collapsed to 0, with no warning. Confirmed live on two real
  September 2026 paychecks (Mohammad Shahid Akhtar, zahra) that both had
  real attended hours and a real line-item amount, yet showed $0 across
  every field. Fixed by falling back to the API's `latest` rate when the
  historical date lookup fails for a future month, instead of giving up.
  The fallback is deliberately not cached under the month's own key, so
  once that month actually arrives its real historical rate gets picked
  up and cached normally.

  Also added a direct `inrAmount` manual-correction field to the
  line-item Invoice/Paycheck PATCH branch (previously only `inrDue` was
  settable there; the legacy flat-shape branch already had this). The
  existing per-line-item PATCH keeps `INRAmount` in sync via deltas
  against a running baseline, so it can't self-heal an already-wrong
  baseline: resaving the same line item amount nets a zero delta.
  Correcting the two real broken paychecks required setting `INRAmount`
  directly, which also now re-derives `Amount` from it (previously that
  only happened via the per-line-item delta path, not a direct
  correction). Both real records confirmed fixed live.
- **Approve payment workflow for Invoices/Paychecks.** `INRDue` already
  defaulted to the full `INRAmount` on creation, but a student marking an
  invoice paid, or staff marking a paycheck received, was a plain
  self-report flag that never touched `INRDue`. Management had a
  separate, disconnected "Edit Due" field they could change anytime, with
  no link between the two. Now, when a row shows `StudentPaidFlag` or
  `StaffReceivedFlag` true while `INRDue` is still greater than 0, the row
  shows a "Needs approval" note and an "Approve (paid in full)" button
  that zeroes the due in one click, with a "Partial…" option to record a
  smaller remaining due instead of the full amount. No new API fields:
  reuses the existing `inrDue` PATCH field on both routes. Verified live
  end to end with a disposable invoice: needsApproval condition triggers
  correctly, full approval zeroes the due and reverts the row to its
  normal actions.

### Added

### Fixed
- **Critical: concurrent writes to the same collection could silently
  delete each other's records.** `sync_table()`, used by every `writeDB()`
  call, deleted every row NOT in the calling request's in-memory snapshot
  before upserting. Two concurrent requests writing the same collection
  each read the table before the other's insert landed, so each snapshot
  excluded the other's new row, and whichever write ran last deleted the
  other's record. Reproduced live: 8 concurrent ticket creations left only
  1 of 8 behind. Fixed with a new Postgres function, `upsert_rows()`
  (insert/update only, never deletes; data/tmp/migration_incremental_writes.sql,
  applied to production), plus a new `deleteRecords()` export for the
  handful of routes that actually remove records (apikeys, services,
  enrollments, invoices, paychecks, and both migrate-monthly merges),
  which now target only the exact ids being removed instead of relying on
  writeDB to infer deletions from what's missing off a snapshot. Verified
  live: the same 8-concurrent-request test now leaves all 8 records
  intact; a mint-then-delete round trip on a real record confirmed the
  explicit delete path still actually removes it from Postgres.
- **Id minting raced under concurrency too, hitting production twice**
  (paychecks, attendanceitems; Sentry: "ON CONFLICT DO UPDATE command
  cannot affect row a second time"). `nextId()` incremented `db.counters`
  purely in memory, so two concurrent requests could read the same
  counter value before either wrote it back and both mint the identical
  id. Fixed with a new Postgres function, `increment_counter()`
  (data/tmp/migration_atomic_counter.sql, applied to production). The
  read-and-increment now happens as one atomic UPDATE, so concurrent
  callers are serialized by the database itself instead of racing on
  JS-level state two separate serverless invocations can never share.
  Every `nextId()` call site across `app/api` was updated to `await` it.
  Verified live: 8 concurrent requests now mint 8 distinct ids with zero
  conflicts. Found via a Sentry review that also surfaced the
  collection-wipe bug above. Both share the same root cause: deriving a
  write from a stale in-memory snapshot instead of a database-atomic
  operation.

### Changed
- **Performance: `writeDB()` now only syncs the collection(s) a route
  actually mutated**, instead of unconditionally re-syncing all 16
  Supabase-backed tables (a real network round trip per table) on every
  single save. `writeDB(db, touchedCollections)` takes an optional array
  of collection keys; every one of the 27 API route files that write to
  the DB was updated to pass exactly what it touches, verified against
  each mutation site individually. No call site was left unscoped:
  guessing wrong here would risk silently dropping data, so anywhere the
  touched set wasn't obvious from the route's own code was checked against
  its actual mutations, not assumed. Omitting the argument keeps syncing
  everything, so nothing outside `app/api/**` needs to change. Confirmed
  live: a single-collection write (mint/delete an API key) leaves every
  other table's record count unchanged. Biggest single latency win in the
  app: most button clicks that save something now do 1 table round trip
  instead of up to 16.
- **Calendar cells (`ScheduleCalendar`)**: a day cell with many sessions
  used to grow unbounded, breaking the week row's height and making a
  busy month's calendar extremely tall. Cells now have a fixed max height;
  once a day has more than 3 sessions the rest collapse into a "+N more"
  pill. Clicking a cell (or its "+N more" pill) opens a popover showing
  every session for that day in full, with the exact same click-to-expand
  attendance/roster behavior each chip already had. The week grid itself
  is now a fixed-height, vertically-scrollable region inside the calendar
  card (nav/legend stay fixed above it) instead of growing the whole page.
  Applies to both calendar boxes in Management's Schedule tab (Open pool
  slots and Service Schedule).
- **TKT-0041 follow-up**: the Teacher Schedule Image's "Batch:" value
  (added earlier in TKT-0041, derived from the teacher's enrolled Batch)
  is removed again per direct request. A teacher can be enrolled across
  multiple batches at once, so showing any single batch name there would
  misrepresent the rest. The "Batch:" label stays on the template (baked
  into the image asset) but its value is now always blank for Teacher

- **TKT-0022**: `POST /api/paychecks` (`action: "generate"`) 500'd generating
  August's draft — traced to `counters.PAY` having drifted behind the
  highest `PaycheckID` actually in use (14 vs 18 real). `nextId()` minted
  an id that already existed; Postgres's batched upsert then rejected the
  whole write ("ON CONFLICT DO UPDATE command cannot affect row a second
  time" — a confusing generic error with no hint at the real cause).

  per call. Fixes the drift for every id prefix, not just PAY, and
  self-corrects going forward regardless of what caused a given drift.

  ("Select service…") that the Batch and Rate selects didn't even have
  once a Service was picked (both auto-select their first option
  immediately). TKT-0047 tracks doing the same across the rest of the
  app — this was one specific instance, not a full sweep.
- Management can now edit a ticket's message after creation, from the
  admin Tickets tab — previously the only mutations were close/reopen.
  `PATCH /api/tickets` takes a new explicit `action: "edit"` (separate
  from the mere presence of a `message` field, so an edit request can
  never accidentally close/reopen a ticket as a side effect, or vice
  versa) — allowed on a closed ticket too, since fixing a typo shouldn't
  require reopening it first.
- Closing a ticket can now include an optional resolution note
  (`CloseMessage`) — shown under the Closed date in the admin Tickets
  tab. Can be added/edited even after the ticket is already closed
  (re-sending `action: "close"` with a new `closeMessage` updates the
  note without touching `ClosedAt`/`ClosedBy` again), and clears on
  reopen since it no longer applies once the ticket's active again.
- **TKT-0021/TKT-0016**: Interview accounts (Teacher/Staff/Ambassador
  tracks) no longer pick their own slot — they request an interview
  against a Service, and Management assigns the actual slot (existing
  open one, or a brand-new one created on the spot) when approving the
  request. Removed the old "Available Interview Slots" picker entirely
  (`availableInterviewSlots` dropped from `/api/me`); `PATCH
  /api/schedule/requests` now takes a `scheduleId` when approving an
  Interview request, validated against the request's own Service and
  against double-booking. Also resolves TKT-0016 by construction — past
  dates never entered the candidate-facing flow in the first place, and
  Management's own slot picker only offers today-or-later.
- **TKT-0015**: The Enrollments tab's enroll form can now mint a one-off
  custom Rate inline, per service row ("+ New rate for this service"),
  instead of being limited to a Service's already-defined Rates — new
  `POST /api/services/rates` appends one Rate to an existing Batch (or a
  role-based Service's own Rates list) without resending the whole Service.
- Ticket # is now shown as its own column on the admin Tickets tab.
- The Worksheets resource page now auto-lists a Google Drive folder's
  contents as clickable cards (each opening its own file directly) when
  WorksheetsLink is a Drive folder link, alongside the existing "Access
  Worksheets" button — new `GET /api/resources/drive-folder`. Requires
  `GOOGLE_DRIVE_API_KEY` to be set; the target folder must be shared
  "Anyone with the link", same assumption the existing link already makes.
- `POST /api/invoices/migrate-monthly` — one-time migration folding
  existing per-subject invoices into the new combined-per-month shape.
  Dry-run by default (`{ apply: true }` required to write); dry-run
  response includes a full pre-migration backup snapshot.
- **TKT-0004**: Student accounts now have an optional Parent Email field
  (Management-only edit), alongside the existing Parent WhatsApp Number.
- **TKT-0005**: Bulk-enroll a single student into several services at once

  instead of a separate Bulk Enroll box.
- **TKT-0006**: Search box on the Services tab, filtering by name.
- **TKT-0007**: Standardized all date displays across the app to
  DD/MM/YYYY (DD/MM/YYYY, HH:MM for timestamps) via a shared

  dashboard, reschedule requests, enrollment Start/End dates, audit

  are unaffected (native `<input type="date">` is always internally

- **TKT-0008**: Fixed the Schedule Image — Student header now shows the

  `Intl.DateTimeFormat` — correctly handles DST).

### Fixed
- `allowedDevOrigins` now also matches `*.trycloudflare.com` — viewing the
  dev server through a `cloudflared tunnel --url` quick tunnel had Next.js
  blocking cross-origin dev requests, so client JS never hydrated. SSR
  HTML still rendered fine, but anything gated behind a client-only mount
  (Nav — hidden until mounted, to avoid a theme/scroll hydration mismatch)

  home page when viewed through the tunnel.
- Code review finding: `generate` could create a duplicate invoice for a

  but hadn't gone through `migrate-monthly` yet — now skipped, same as

- Schedule Image: every grid cell was filled with the role's color
